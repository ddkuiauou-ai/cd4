## 2. 아직 확인할 가설

1. 실제 거래일 명부를 순서대로 적용하면 14개 이탈이 여러 날짜에 나뉘어 매 단계 보호 조건을 통과할 수 있다. 실제 중간 원본을 적용한 검증은 아직 없다.
2. 중간 명부가 완전하고 각 변화가 실제 종목 변화일 수 있다. 조건 통과만으로 정확성을 증명하지 않으며 원본의 누락·중복·종목 연결과 변화 목록을 함께 확인한다.
3. 빈 기업 캐시는 과거 일시적 조회 오류가 정상 빈 값으로 저장된 결과일 수 있다. 최초 오류 원인은 미확정이며 현재 직접 조회와 캐시·웹 차이가 확인된 근거다.
4. 진행 중인 반복 재처리 수정이 기존 실패 실행에서도 원래 전체 후처리 요구를 유지할 수 있다. 서비스가 보강한 보고서, 원본 JSON 사용 경로, 구버전 입력의 `finalize=True / finalize_dates=[]`를 따로 검증해야 한다.

## 3. 최소 수정 범위

### KONEX: 보호 조건을 유지하는 순차 복구

- 기존 10% 보호 조건을 유지한다. 이전 계획의 종목별 예외 통과 기능은 우선 수정안에서 제외한다.
- 첫 실행 직전 KONEX 유효 기준일과 미완료 날짜를 다시 조회한다. 현재 기준선은 2025-09-22이므로 그 이후부터 2026-10-02까지의 실제 거래일을 오래된 순서로 선택한다. 재개할 때는 master head만 보고 다음 날로 넘어가지 않고 기존 업무 보고서와 가격 검증으로 실패 당일의 미완료 여부를 먼저 확인한다. 달력상의 모든 날을 거래일로 가정하지 않는다.
- 중간 날짜는 하루씩 `refresh_security=True`, `finalize=False`, KRX 출처로 실행한다. 기존 내부 입력 생성 경로는 KONEX·price 선택과 이 옵션을 지원한다. 단순 `history`는 종목마스터를 갱신하지 않으므로 복구 경로로 사용하지 않는다.
- 하루의 업무 결과, 명부 영수증, master 변화·기준일, 필요한 가격 저장 검증을 확인한 뒤 다음 날짜를 발행한다. 현재 다일 Workflow는 실패 후에도 다음 날짜를 처리하므로 그대로 사용하지 않는다. 기존 단일 날짜 실행을 순서대로 제어하고 필요하면 작은 로컬 실행 도구만 추가한다.
- 같은 KONEX의 유효 기준일보다 이른 입력은 historical 분기로 master를 변경하지 않는다. KOSPI·KOSDAQ의 더 최신 명부는 거래소별 KONEX 기준일을 올리지 않는다.
- 검증 실패·부분 완료·원본 불가이면 해당 날짜에서 중단한다. 반복 실패 구간의 원본과 종목 변화를 조사한 뒤 같은 날짜를 복구한다. 다음 날짜로 건너뛰거나 임계값을 넓히지 않는다.
- 중간 날짜에는 전시장 최신값·회사 합산·순위를 최종화하지 않는다. 마지막 목표일에서 KONEX의 필요한 전체 데이터를 완료하고, 성공한 KOSPI·KOSDAQ의 원본/정제 SHA·DB head·영수증·실제 저장값을 검증한 뒤 전체 후처리를 수행한다.

명부 반영과 가격 적재는 별도 트랜잭션이다. 명부 검증 실패 시 master 변경은 없어야 하지만, master commit 후 가격 적재가 실패하면 master commit은 남을 수 있다. 이때도 다음 날짜를 중단하고 같은 날짜 재처리에서 영수증과 연결을 검증한다. 완료된 master를 무조건 되돌리는 기능은 추가하지 않는다.

### 반복 재처리: 원래 전체 후처리 요구 보존

- 수정 전 결함을 회귀 사례로 고정한다. 실패한 거래소만 남은 보고서에서 전체 시장 선택 여부를 다시 추론해 원래 후처리 요구를 지우지 않도록 한다.
- 원래 요청한 최종화 날짜와 미완료 `blocked / UPSTREAM_FAILED`, `failed` 날짜를 기존 입력·보고서 계약을 통해 다음 재처리에 전달한다. 단일 시장·부분 데이터·history에는 전체 후처리 요구를 새로 부여하지 않는다. 세 시장·전체 데이터를 선택했어도 원래 명시적 `finalize=False`이면 그대로 유지한다.
- 메인 작업에서 진행 중인 planner·보고서 조회 수정에 맞춰 GUI/CLI 서비스 경로와 기존 실패 Run 호환을 검증한다. 읽은 시점에는 원본 요약 JSON에 원래 요구가 없어 직접 planner 호출에서 요구가 빠질 수 있으므로, 지원하는 재처리 경로가 요구를 복원하는지 확인한다.
- 실제 Workflow 실행 경로를 수정할 필요가 생기면 해당 변경에 한해 기존 history 재생 호환을 검증한다. 별도 상태 저장 시스템은 추가하지 않는다.

### 웹: 조회 오류·캐시·기준일

- 랭킹이 실제 호출하는 기업 목록·개수, 종목 목록·개수, 관련 가격 조회에서 DB 오류를 `[]`, `0`, `{}`로 바꾸지 않는다. 정상 0건은 빈 결과로 처리하고 오류는 기존 오류 경계로 전달한다.
- 메인 작업의 공통 캐시 정책을 재사용한다. 개발은 캐시 우회, 서버 운영은 명시적 300초 재검증과 새 namespace를 적용해 기존 빈 캐시를 피한다. 종목 랭킹 목록·개수에 아직 같은 오류 처리와 기본 캐시 정책이 남아 있는지도 적용 범위에 포함한다.
- 실패 응답으로 정상 캐시를 새로 채우거나 유효 기간을 연장하지 않는다. 정상 캐시가 있는 경우와 없는 경우를 모두 시험한다. 만료 후 첫 응답에는 이전 성공값이 나올 수 있으므로 재검증 완료 후 정상 최신값으로 바뀌는지 확인한다.
- 기업 기준일은 이미 조회하는 `company.marketcapDate`, 종목 랭킹은 `security_rank.rank_date`를 사용한다. 대표 종목의 최신 원시 가격 날짜를 회사 순위 기준일로 추정하지 않는다. 화면·메타데이터·CSV 파일명의 의미를 맞춘다.
- 기준일을 실제 처리 시각으로 표시하지 않는다. 기존 DB 필드로 정확한 처리 시각을 알 수 없는 경우 별도 완료 기록 연동을 추가하지 않는다.
- 웹의 Temporal 상태 표시, 새 webhook·무효화 endpoint·Activity·배포 연동은 추가하지 않는다. 기존 Temporal 관리 화면과 로그를 사용한다.

과거 순위와 더 최신 원시 가격 이력을 함께 읽는 문제는 별도 발견이다. 가격 조회의 as-of 제한이나 모든 지표 화면의 개편은 이번 빈 기업 화면 복구의 필수 수정으로 묶지 않는다. 기준일 테스트에서는 회사 합산/순위 날짜와 가격 이력 자체 날짜를 구분한다.

| 기존 보고서 호환 | 기존 full daily 실패, 부분 재처리 실패, `finalize=True / finalize_dates=[]`, 후처리만 실패한 보고서로 실제 지원 서비스/CLI 경로를 검사한다. 수집만 성공하고 최종화 요구가 사라지는 경우는 실패다. |
| 웹: 직접 조회 → 조회 함수 → 화면 | 동일 테스트 DB·필터·페이지 기준으로 ID·행 수·총수·금액·순위·기준일이 일치한다. 조사 당시 20행/2,601개는 기준선이며 복구 후 고정 기대값으로 쓰지 않는다. |
| 웹: 오류 → 복구 | 목록·개수·관련 가격 각각 격리 오류를 주입한다. 정상 0건으로 캐시하지 않고 DB 복구 후 같은 프로세스 재요청이 정상 결과를 읽는다. 정상 빈 목록도 오류와 구분한다. |
| 웹: 오래된/빈 캐시 및 성공 캐시 갱신 | 이전 namespace 빈 캐시를 새 정책으로 읽지 않는다. 개발 조회는 DB 변경을 반영하고 운영 모드는 만료·재검증 완료 후 새 정상 결과를 반영한다. 갱신 실패 후 회복도 검사한다. |
| 로컬 브라우저 | 기업 첫/다음 페이지, 종목 탭, 모바일 목록·데스크톱 표·CSV의 값과 DB 기준일이 일치한다. Temporal 복구 전 기존 2025-09-22 회사 랭킹이 정상 표시되면 웹 빈 화면 복구는 별도 통과다. |

로컬 fixture/테스트 DB의 명부·원본과 장애 주입을 사용한다. 업무 public schema에는 테스트 실패를 주입하지 않는다. 기존 집계·rollback 테스트와 필요한 경로의 회귀 테스트를 실행하고 웹은 타입 검사를 별도로 수행한다. Next 빌드가 타입/린트 오류를 무시하도록 설정돼 있으므로 build 성공만으로 통과 처리하지 않는다.

## 5. 실제 데이터 검증과 운영 반영 순서

1. 위 로컬 웹·격리 DB·재처리 회귀 결과를 기록한다. 공유 작업의 변경 파일과 검증 결과를 재사용해 중복 수정을 피한다.
2. 로컬 검증 통과 뒤 실제 KONEX 기준일과 원본 접근 가능 범위를 다시 확인한다. 접근할 수 없는 중간 거래일은 해당 구간에서 조사하며 검증 없이 건너뛰지 않는다.
3. 실제 거래일 하나를 반영하고 원본·변화 목록·영수증·master를 확인한다. 통과한 뒤 다음 날짜로 진행하며 동시에 여러 날짜를 발행하지 않는다.
4. 마지막 목표일에 이전 성공 데이터의 저장값/영수증 검증, KONEX 대상일 완료, 세 시장 전체 후처리, 읽기 전용 독립 audit 순서로 진행한다.
5. 정상 캐시 재검증 후 웹 금액·순위·기준일을 대조한다. 기본 standalone 운영은 서버 재검증 결과를 확인하고 정적 export 운영은 재빌드·재배포 HTML을 확인한다. 실제 배포 방식과 운영 반영은 로컬 검증 이후 결정한다.

결과에는 원본 날짜·hash, 변경 목록, Workflow/run ID, 업무 결과, master/최종화 영수증, 독립 audit, 웹 확인을 기록한다. 기존 보고서와 로그를 활용하고 새 상태 시스템은 만들지 않는다. 테스트 통과, 실제 명부 복구, 목표일 후처리, 운영 배포 완료를 구분한다.

로컬 최소 수정과 웹 21개·Temporal 선택 회귀 303개 검증을 완료했다. 브라우저·모바일·CSV·DB 직접 조회 대조도 확인했다. 결과는 [로컬 검증 기록](ranking-fix-verification-2026-10-05.md)에 있다. 실제 중간 거래일 catch-up과 목표일 전체 후처리 성공, 운영 반영은 아직 실행하지 않았다.
