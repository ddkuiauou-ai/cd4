## 실행 순서와 통과 조건

1. 현재 코드·환경·데이터 상태를 기준선으로 보관한다. 기존 회사/종목 ID, 연결, 과거 행, 날짜와 순위를 보존한다.
2. KONEX 116개→107개(기존 누락 14개, 신규 5개)를 재현하는 격리 테스트를 만든다. 최신 날짜 직접 반영은 차단되고, 단계별 순차 명부 반영은 성공하는지 검증한다. 실패 시 변경 0건, 과거 날짜가 현행 명부를 되돌리지 않는지도 확인한다. 합성 테스트는 실제 KRX 원본의 완전성을 증명하지 않는다.
3. 반복 재처리에서 원래 전시장 후처리 요구가 빠지는 결함을 최소 수정한다. 전체 실패→재처리 실패→다음 재처리 성공에도 마지막 전체 후처리가 유지돼야 한다. 단일 시장·부분 수집은 전체 후처리 권한을 얻지 않아야 한다.
4. 회사 목록·총수, 메인에 필요한 가격·검색 조회의 오류를 정상 빈 값으로 반환하지 않는다. 개발 중에는 캐시를 우회하고, 서버 운영에서는 공통 300초 재검증과 새 캐시 namespace로 기존 빈 캐시를 피한다. 오류가 있는 조회를 성공으로 저장하지 않는지 테스트한다.
5. 메인은 실제 로딩과 정상 빈 결과를 구분한다. 오류는 기존 오류 화면을 사용한다. 가격이 없는 종목, 집계 기준일, 실제 전체 건수도 확인한다.
6. 로컬 브라우저에서 메인 표·검색·기준일·빈 상태를 확인하고 조회 실패→복구 테스트를 수행한다. 정상 데이터가 있는 상태에서 기존 빈 캐시에 고정되지 않아야 한다. 타입 검사는 변경 전 오류와 비교하며 빌드의 오류 무시 설정을 검증으로 간주하지 않는다.
7. 실제 따라잡기를 실행할 때는 KONEX의 현재 기준일을 다시 읽고, 기준일 이후 실제 거래일을 하나씩 명부 반영한다. 날짜별 완료 검증을 통과한 뒤 다음 날짜로 진행한다. 중간 날짜의 전시장 최종화는 생략하고 목표 날짜 2026-10-02에서만 성공한 다른 시장의 영수증·저장 내용을 재검증하여 전체 최종화한다.
8. 실제 업무 복구 후 독립 SELECT audit로 최신값·회사 합산·회사/종목 순위·기준일·ID/이력 보존을 확인한다. 서버 운영은 재검증 이후 요청, 정적 export는 재빌드된 HTML을 각각 확인한다. 실제 운영 배포 방식 확인 및 반영은 로컬 검증 이후 진행한다.
